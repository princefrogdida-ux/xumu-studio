## 1. 目标

把已经跑通的本地工作台优化为便于持续制作、定位问题和恢复数据的 V1。优先解决明确的可靠性问题，补齐现有验收，再减少制作中的重复操作和长期数据积累带来的开销。

本轮评估认为 React Flow、React、TypeScript、Fastify、SQLite 和独立 worker 的路线仍适合单人本地版。尚无证据支持更换画布库、引入 Redis、拆成微服务或整体重写。具体性能改善幅度需要测量，不能把代码中的开销直接描述为已发生的严重卡顿。

期望结果：

1. 启动、停止、备份和异常恢复有可观察结果，单个损坏的导出记录不拖垮整套工作台。
2. 在一千条任务历史和一百节点的样例下，读取和交互成本受到控制。
3. 用户从分镜、历史、缺失项直接到达相应操作，清楚知道下一步是什么。
4. 真实调用先完成有限、明确的实测，再讨论服务扩展；真实和模拟来源始终准确。
5. 每一批优化有独立证据、兼容说明和回退路径。

## 3. 范围、优先级与风险

P0：可靠性与交付基线，应先处理。P1：常规制作体验与持续使用性能。P2：按实测或使用频率再决定的增强。

| 编号 | 优先级 | 工作项 | 主要价值 | 风险 |
|---|---|---|---|---|
| OPT-01 | P0 | 版本基线与独立安装验收 | 成果可追溯、可复现 | 首次提交需单独授权；安装受网络影响 |
| OPT-02 | P0 | 导出恢复容错与 Windows 停止流程 | 防止单个坏记录阻止启动，减少半成品 | 涉及进程与持久化；必须隔离测试 |
| OPT-03 | P0，条件满足后执行 | 真实服务有限验收 | 确认实际协议、效果和恢复能力 | 收费、凭证与未知远端状态 |
| OPT-04 | P1 | 任务分页、摘要与自适应读取 | 避免长期历史全量反复读取 | 分页遗漏旧选中版本、响应乱序 |
| OPT-05 | P1 | 画布更新与输入计算优化 | 拖动成本集中于受影响节点 | 撤销、保存和输入变化提示可能回归 |
| OPT-06 | P1 | 制作进度、定位与版本操作 | 减少往返和重复连线 | 自动建节点若不去重可能污染画布 |
| OPT-07 | P1 | 缺失素材映射与交付记录 | 导入后恢复更明确、旧包更易找 | 错误重连可能破坏来源或旧快照 |
| OPT-08 | P1 | 本地诊断与渐进模块拆分 | 问题可定位、修改影响更小 | 日志泄密、重构改变请求行为 |
| OPT-09 | P2 | 按需加载、素材列表与空间管理 | 改善首屏和大量媒体管理 | 页面状态丢失、误删共享素材 |

安全操作：读代码、记录指标、只读诊断、草案与验收文档。

可能影响当前项目的操作：改代码、公开 API 分页、数据库增加索引或健康记录、启动方式调整。实施前保留版本和完整数据备份，优先在独立分支/工作树与隔离数据目录进行；当前没有首个提交，应先建立基线或保留可核验代码副本。

高风险操作：真实收费、删除媒体、覆盖 .env、替换原数据恢复、公网发布。草案不提供这些行为的执行授权；需要检查后续明确授权和实际范围。

## 4. P0：先稳住交付基线

### OPT-01：版本基线、独立安装和重复启动

旧行为：本机已有依赖可运行；没有首次 Git 提交；独立目录复用依赖后启动通过，全新联网安装未完成。

目标行为：能够指出哪份代码对应已验收成果，并在不复制 node_modules、缓存、data 或 .env 的独立环境中按文档启动。

执行步骤：

1. 复核 .gitignore 和候选文件，确认没有真实密钥、数据库、媒体、输出、私有回执和依赖目录。
2. 后续获得提交授权后，再建立首次基线提交；各优化批次单独提交。分支、工作树与远端备份分别处理，不自动推送。
3. 在新的验证目录/Windows 账户或干净测试机使用 Node 24.14 或更新的 24.x、pnpm 11.19 和锁文件安装，保持供应链校验；网络失败保留记录，不升级包或跳过校验以换取成功。
4. 增加只读环境检查入口：运行时版本、必要文件、端口占用、数据目录可写、API 与 worker 状态；只输出状态，不输出 .env 内容或密钥。
5. 按 README 完成开发启动、生产 API + worker 启动、Mock 请求、重复请求去重、停止和再次启动。测试数据独立于用户 data。

验收：干净环境从安装到三镜头模拟 ZIP 导出完整通过；端口冲突说明具体占用端口，不盲目杀进程；命令记录包含实际版本、退出码和结果。Git 提交状态与安装结果分别报告。

### OPT-02：损坏记录容错、正常停止与异常恢复

旧行为：单个损坏 JSON 可能让 onReady 失败；dev 使用 kill 停子进程，Windows 不能据此保证 API 等待打包和 worker 收尾。

目标行为：健康项目和有效导出记录能继续使用；正常停止有明确完成结果；强制中断仍按既有规则恢复，绝不自动重交生成。

功能与技术要求：

- 对每个导出 sidecar 做大小、字段和状态校验，逐文件捕获异常。忽略并记录无效记录的诊断，不自动删除或改名原文件，也不因它拒绝整个服务启动。
- 成功 ZIP 仍必须对应合法成功记录并通过 checksum。记录缺失/损坏时不猜测成功，不直接开放 ZIP；提示重新导出。
- dev 的 API/worker 增加受控 IPC 停止信号。API 停止接收新请求，等待已受理导出完成，关闭数据库；worker 停止认领新任务，结束当前有限步骤并释放资源。Vite 的停止方式单独核实。
- 父进程等待子进程退出并记录结果；建议正常停止等待上限 60 秒。超时可对已验证属于本项目的子进程强制结束，明确报告“强制停止/可能遗留待确认任务”，不能标为正常收尾。长时间等待需持续显示实际状态。
- 备份前核实相关进程退出、端口释放和数据文件句柄可读，不能仅以 kill 返回成功作为证明。IPC 不经未鉴权的公网/本地 HTTP 停止接口开放。
- 在隔离目录验证进程中断、磁盘写入失败和文件改变；先使用可控 I/O 故障注入，后补真实子进程测试，避免把系统盘填满。

验收：一个坏 sidecar 与一个正常 sidecar 共存时，API 启动且正常包可下载；坏记录有可读诊断，旧文件保留。正常停止后端口全部释放；打包中的正常停止等待发布或明确失败。强杀后半成品不可下载，已有 building 记录转失败，submitting 无远端 ID 转 unknown，收费 POST 次数不增加。新增测试覆盖 1 GiB 边界判定和大包流式输出，不把小夹具的大小校验当作真实 1 GiB 打包验证。

### OPT-03：补齐具体真实服务验收

这项属于现有 V1 的未完成验收。优化工作的本地部分可以继续推进，不必等待用户选定服务；真实步骤依赖具体地址、模型、协议、凭证和明确费用额度。

执行顺序：

1. 本地核实配置完整性、服务摘要、能力与参数；默认真实开关继续关闭。检查配置不调用可能收费的“测试生成”接口。
2. 确定一个有限的测试清单，列出调用类别、最大提交次数/候选数、费用上限及价格来源；费用未知时明确记录，人工约束请求次数不能被宣传为金额硬限制。
3. 授权后依次完成文本拆解、单张参考图图片生成、单镜头视频；协议不匹配时停止分析，不自动换服务或提交格式重试。
4. 单镜头通过后完成三至五镜头：同一角色跨镜头、一次重新生成与候选选择、图片→视频、刷新恢复、有序 ZIP。
5. 记录服务与模型标识、实际参数、耗时、人工效果评价、已知协议限制和可核实费用；原始私有响应继续只留服务端。

验收：实际图片/视频可预览、下载并对应固定快照，来源真实标记正确；响应丢失仍进入待确认，不自动重新收费；导出不含凭证或签名地址。效果按参考图遵循、镜头描述、时长/尺寸和可用性逐项记录，不保证跨镜头完全一致。

后续可考虑服务端持久化的真实提交次数限制。若提出金额限制，必须有可信价格和保守预留；unknown 不自动释放预留，重复 requestKey 不重复计数。该增强另列为后续范围，不能把尚未实现的控制作为本次真实测试保护。

## 5. P1：持续使用性能

### OPT-04：任务查询拆成活动摘要、历史分页与详情

旧行为：前端持续读取所有任务、生成记录和输入快照，全量 JSON 比较。

建议行为：活动任务轻量更新；历史按需查看；已选版本即使很旧也始终可读。

技术要求：

- 公开接口新增活动摘要和历史游标分页，建议每页 30 条、最多 100 条。使用稳定的排序键与快照边界，不能只用 offset 导致新任务插入时漏项或重复。
- 摘要包含 taskId、nodeId、kind、mode、status、updatedAt 和安全错误摘要；完整输入快照、草稿和候选详情按任务/生成 ID 读取。
- 活动状态仍按真实数据库读取。活动任务存在时保持约 1.2 秒刷新；无活动任务的前台页改为约 10 秒轻量检查；隐藏页面建议约 30 秒检查。恢复焦点、手动刷新和提交后立即刷新。轮询不能改变 worker 查询远端的节奏。
- 同一项目请求不重叠；给请求添加递增序号或取消控制，避免手动刷新与自动刷新乱序覆盖。切项目后旧请求不能改变当前列表。
- 更新只合并实际变化记录，替代每次全量 JSON.stringify。为长期记录建立按 ID 缓存，缓存大小有上限。
- selectedGenerationId、历史选用素材及正在检查的任务需要独立详情加载，不能因为它不在第一页就误判不存在。分页只影响公开查询；worker、恢复、导出及来源追溯不得误用第一页。
- 数据库索引先检查已有索引与查询计划，再按需要添加。若增加索引，采用显式迁移，保留原任务 JSON、requestKey、fingerprint 和历史。

验收：一千条历史任务、少量活动任务的隔离夹具中，默认历史页不超过页大小，活动响应不携带全量快照；旧选用候选仍显示并能导出。稳定完成状态下，持续观察一分钟，轮询频率按新规则下降。新任务插入、分页、切项目和响应乱序无重复/漏项/串项目；生成幂等与恢复回归通过。

### OPT-05：画布局部更新和输入计算

旧行为：拖动更新复制全份文档、比较全份 JSON；业务节点订阅整份文档，位置变化也可能重新解析生成输入。

建议行为：只更新受影响节点；坐标、视角和选中状态与生成业务输入的计算分离。

技术要求：

- 先采集 React 渲染次数、编辑耗时、长任务和拖动帧间隔，确认主要开销。已有 DomainNode memo 和 selector 是基础，不重复以“加 memo”替代实际优化。
- 为移动、尺寸、视角等高频动作增加专用不可变更新，未改动节点及其 data 保持引用；一次拖动仍只有一个撤销记录，拖动最终坐标必须保存。
- 节点订阅自身数据和实际依赖的角色、分镜、资产、任务；维护可复用 ID 索引，减少重复 find。根工作台减少对所有文档变动的订阅。
- 输入计算按文字、连线顺序、选中版本、参考资产 checksum、模型和参数失效。位置、尺寸和视角变化不触发生成 fingerprint 重算；真正业务输入改变必须及时标记。
- React Flow 回调、默认选项和 nodeTypes 保持稳定引用；保留卡片拖动、编辑输入、连线校验和按需视频播放。
- 保留现有完整快照撤销作为首轮兼容实现，先限制高频复制；增量撤销不与首轮改动一起引入。当前 80 次历史上限作为既有基线，后续按内存数据再调整。

依据：减少对频繁变化的大数组订阅、保持组件/回调引用稳定，与 [React Flow 官方性能建议](https://reactflow.dev/learn/advanced-use/performance)一致；是否需要额外优化以本机测量决定。

验收：一百节点/一百五十连线和含生成节点的独立样例中，拖动单卡片不让所有未关联业务节点重复解析输入；缩放平移不改变生成摘要。撤销重做、复制、保存恢复、运行中输入固定、版本切换和缺失素材校验不回归。记录优化前后同机三次测量的中位数与 p95；若不能证明改善，不宣称性能提升。

## 6. P1：制作流程与恢复体验

### OPT-06：进度提示、跳转定位和生成节点准备

功能要求：

- 分镜列表显示图片/视频选用、相关运行任务和“可以交付/需要处理”的摘要；保留上游变化提示。状态来自 Shot、Asset 和 Task，不新增第二套手工完成状态。
- “查看节点”“编辑角色/场景”“查看缺失镜头”统一打开相应视图、选中并定位；找不到节点时说明业务记录仍存在，允许明确放入画布，不能无提示重复创建。
- 从分镜提供“准备图片节点”“准备视频节点”：基于显式选择建立节点、镜头关联和有类型引用。已有多个可用节点时先列出选择，不猜测该复用哪个节点。
- 准备动作是一次可撤销的项目编辑；再次操作优先定位已关联节点，重复点击不制造重复连线；只连接确定的输入，超过能力限制时说明原因。
- 历史区清楚区分“供下游使用”和“镜头最终选用”，同时显示当前选择与实际来源；选用后分镜状态同步。错误说明给出能执行的下一步，例如重新上传、选择版本、恢复服务配置或人工核实远端任务。
- 一次最多准备当前镜头的节点，不做自动逐镜生成。按钮创建结构、打开视图和切换版本均不得提交模型请求。

验收：普通用户按页面提示完成三镜头模拟素材包；从任务跳到对应节点后卡片可见；从缺失项到镜头编辑不超过两次明确操作；重复准备节点不增重复边；撤销恢复原文档；操作日志/假服务确认额外生成请求数为 0。额外的点击数改善须有优化前后的实测记录。

### OPT-07：外部导入后的缺失素材映射与导出记录

旧行为：JSON 导入保留缺失占位，需手工上传并分别替换引用；最近导出 ID 主要保存在浏览器 localStorage，没有可浏览的服务端历史入口。

建议行为：提供明确的映射预览和可追溯的交付记录。

- 导入结果按缺失资产列出名称、类型、checksum 和受影响记录；用户选择已授权素材或上传新文件，再查看将修改的当前引用。
- 应用映射重写当前项目中该缺失 ID 的所有匹配引用，以一个 revision 编辑提交并支持撤销。不能直接改写原资产、旧任务快照、历史生成来源或其他共享项目。
- 若生成节点映射后的选用资产不再对应原 selectedGenerationId，清除该节点当前的历史选择 ID，按替代资产的实际来源展示；原生成记录及其候选保持不变，不能把上传替代物标成那次模型的结果。
- 类型不匹配拒绝；checksum 不同清楚标记为替代素材，不能声称找回原文件。重新上传得到新稳定 ID，不制造虚假的 generation provenance。
- 先只支持当前编辑引用的恢复；完整历史迁移、ZIP 导入和跨电脑自动恢复不在此项内。
- 增加按项目分页读取导出记录和“重新下载”入口，显示时间、revision、完整/部分状态、模拟/真实混合来源与问题。校验原 ZIP，不能用当前项目状态重写旧包清单。
- 导出取消响应不明时，先通过服务端记录识别仍在运行的包并显示状态；找回操作不创建新包。浏览器清理 localStorage 后仍能查看现有导出。

验收：一个缺失图被角色、Media 节点、生成配置和多个镜头引用时，映射后当前引用一致、保存刷新可恢复，撤销还原缺失状态；旧任务 fingerprint 和其他项目不变。清理浏览器缓存后已有 ZIP 仍可找回；损坏包拒绝下载，部分包保留缺失说明。

## 7. P1：诊断与维护

### OPT-08：本地健康信息、脱敏诊断和渐进拆分

功能与技术要求：

- 健康信息分别显示 API 可达、worker 最近心跳、当前活动任务、真实调用配置状态和数据版本。worker_lock 空不代表 worker 停止，因为当前实现会释放锁；运行健康需独立心跳。
- 心跳建议每 5 秒更新，超过 20 秒标“暂未收到心跳”，不直接宣称任务失败。排队但没有心跳时提示启动 worker；显示本地时间和最后成功时间便于排查。
- 阶段标签统一来源，避免 capabilities 残留 M4；区分应用版本、方案版本、数据版本和开发阶段，不以方案版本冒充软件版本。
- 错误记录包含本地 requestId、操作类别、项目/任务 ID、错误码、时间及安全诊断；继续禁止密钥、鉴权头、私有 URL、回执原文和用户完整提示词自动写日志。
- 错误使用稳定 code 决定操作能力，逐步替换按中文错误字符串前缀判断“可重新查询”的逻辑。中文消息允许改进，业务状态保持一致。
- 在修改对应功能时再拆出项目会话/保存 hook、画布工具、任务读取、导航与 API 路由模块。避免一次性把所有文件格式化或重构。
- 公共类型和 Zod 保持共享，接口增量集中记录；诊断导出也须按字段允许列表处理，保留私有服务端数据边界。

验收：只停隔离 worker 时，界面能显示排队与心跳缺失，重启后恢复；关闭网页不停止实际 worker。中文错误改文案不影响重查询门禁；同一请求可按 requestId 关联安全日志。虚构密钥/签名 URL 测试不出现在日志、诊断包或浏览器。模块拆分后现有关键测试通过，公开行为不变。

## 8. P2：测量后推进的增强

### OPT-09：加载、媒体列表和空间使用

1. 按需加载 TransferPanel、任务历史和库页面，声明 lazy 在模块顶层，提供加载状态和错误恢复。画布核心先保留稳定加载；切换视图不能重置未保存内容或项目会话。[React 官方 lazy 文档](https://react.dev/reference/react/lazy)支持按首次渲染延迟加载代码。
2. 对素材列表增加类型、来源、可用状态和是否选用筛选；先采用分页与按 ID 获取当前引用，再决定是否需要虚拟列表。即使选择的素材不在当前页，画布、输入解析和导出也必须能读取它。
3. 测量缩略图和视频 Range 的重复校验成本。先考虑同一时刻相同文件校验合并与有限并发，结果不跨请求长期复用；不以 size/mtime 替代完整 SHA-256，不跳过生成前、交付前和实际打包中的校验。跨请求缓存若会改变完整性保证，需另写生效修改方案。
4. 显示媒体、导出包、临时文件和备份占用的只读统计。首轮只报告空间，不自动清理。
5. 后续空间清理先只处理用户明确选中的旧导出包，列出影响后再执行。原素材、任务历史、私有回执与共享引用不进入首轮清理范围；不增加“自动删除未选候选”。

验收：记录优化前后首屏实际请求字节、加载时间和首次切换耗时，不能只靠把文件拆成多个 chunk 消除体积警告；两千素材夹具列表操作正常，旧选用版本不丢失；相同大小损坏仍被发现。没有充分收益时允许延期，不强行引入新包。

## 9. 实施批次、测试与交付标准

建议按依赖分批，不承诺未经测量的固定工期。真实验收可以独立于本地优化排期，但收费步骤有明确先决条件。

| 批次 | 内容 | 开始条件 | 交付与结束条件 |
|---|---|---|---|
| A：可靠性与复现 | OPT-01、OPT-02 | 后续用户授权实施；代码/数据基线可核验 | 独立安装证据、坏记录容错、Windows 正常/异常停止记录、备份说明更新 |
| B：读取与画布 | OPT-04、OPT-05 | A 的恢复与回退条件具备 | 一千历史任务、一百节点基准，接口/输入/保存回归通过，实测成本改善 |
| C：制作与恢复体验 | OPT-06、OPT-07、OPT-08 的导航/错误部分 | B 的按 ID 详情加载可用 | 三镜头操作录屏/截图、缺失映射撤销、导出记录恢复、明确诊断 |
| D：真实验收 | OPT-03 | 具体服务、协议、凭证、费用授权齐全 | 单镜头与三至五镜头真实报告，兼容限制与来源准确 |
| E：测量驱动增强 | OPT-08 的剩余拆分、OPT-09 | 基准或实际使用证明有收益 | 首屏/素材量/空间报告；低收益项目可暂缓 |

性能采样约定：同一 Windows 机器、固定浏览器与分辨率；区分生产构建与开发模式；相同夹具分别测冷启动和热运行，各至少三次；记录硬件、节点/连线/历史量、请求字节、耗时分布与内存。建议初步门槛为：一千历史任务首屏只加载规定页大小；一百节点/一百五十连线连续操作无单次超过 500 ms 的页面冻结；受优化操作的 p95 不劣于基线。若实测表明门槛不合适，先在实施方案里说明原因并修订，不能测完后静默改标准。制定方案时没有这些量化结果，执行后的记录见当前索引和优化验收。

每批通用交付：

- 实际代码与已更新 API/操作文档，必要的迁移和回退说明。
- 受影响关键规则的测试与浏览器证据；验证仍采用现有 `scripts/project.ps1 typecheck/test/build`，新增脚本按届时真实接口落地。
- 测试只使用独立 data、假服务和 MockProvider；网络、磁盘、进程故障不直接作用于用户 data。
- 核验旧项目名称、revision、内容、旧任务/输入快照、选用资产和媒体校验值；未触及旧数据不得改变。
- CURRENT_PLAN 写实际结果、未完成事项和下一步；CHANGELOG 记录最终变更，不能提前打勾。

本轮文档交付标准：依据可定位；草案/生效状态一致；本地链接有效；旧方案及阶段状态保留；不把建议阈值或拟实现功能写成已验证结果。

## 10. 兼容、限制与回退

兼容要求：

- 保留旧项目文档 1～4 的既有升级/导入能力，以及旧 task/generation ID、requestKey、fingerprint 和服务摘要语义。
- 增量 API 先与前端成套更新；旧接口需要迁移时标明兼容期，不突然改变既有无参数调用的返回形态。
- 内存索引、按需加载和界面跳转通常不改持久化结构；任务索引、worker 健康记录如需 schema 升级，采用显式事务迁移，并保留失败原数据。
- 新查询不改变任务执行并发、远端轮询、付费提交和 unknown 恢复规则。连接、打开页面、映射素材、切换版本、刷新和撤销仍不能生成。
- 保存冲突继续拒绝静默覆盖。重连素材和准备节点仍必须经过现有 revision 和保存队列。

本方案不安排多人账号、公网发布、自动整集生成、完整剪辑器、桌面安装包、训练模型或自动删除原素材。新依赖不是默认选项；确有必要时先核实官方文档、许可证、固定版本和 Windows 支持，不顺带升级整套依赖。

回退步骤：实施前核验代码基线，停止本项目服务后备份完整 data；每批记录对应代码版本、数据版本和备份路径。代码改动可回退到上批基线；涉及数据迁移时必须先停服务，保留现有 data，再恢复与旧代码匹配的备份，不能让旧代码直接读取不兼容的新数据。回退不能撤销已发生的远端收费请求，真实 unknown 仍须人工核实，不能恢复旧数据库后自动补发。

## 11. 官方参考与生效方式

2026-10-05 核实，仅采用官方资料：

- [React Flow 性能](https://reactflow.dev/learn/advanced-use/performance)：支持稳定引用、缩小状态订阅和减少无关渲染的方向；不是本项目性能结果。
- [React lazy](https://react.dev/reference/react/lazy)：按需加载与 Suspense、加载失败边界；不能仅通过拆包证明性能改善。
- [Node 24.14 child_process](https://nodejs.org/download/release/v24.14.0/docs/api/child_process.html#subprocesskillsignal)：Windows 的 child.kill 会强制结束目标进程，不能假设执行 SIGTERM 收尾；支持 OPT-02 的判断。

制定方案时本地代码检查确认问题入口，当时尚未重新测量延迟、内存、故障恢复或真实费用；后续执行证据按当前索引和优化验收记录，真实费用仍未验证。

本方案已按用户 2026-10-05 的实施指示生效，开发基线更新为 V1.6。实际完成、条件未齐全与延期项登记在 CURRENT_PLAN，经过写入 CHANGELOG；可选增强须有测量依据。真实服务与费用、Git 提交/推送、删除、恢复覆盖和部署分别检查已有授权，不能从“优化方案生效”推断全部授权。
